# Duplicate deliveries before an incremental merge

Deduplicating the incoming relation before the incremental merge restored one row per event in this synthetic incident. The executed fixture contains 121 deliveries for 100 event identities. The broken model produces 20 duplicate identity groups; the fixed model produces zero and retains 100 events. These are generated demonstration results, not a description of an employer's systems or a claim of production impact.

The initial batch contains one delivery for each identity. A later batch resends the first twenty events with newer source update timestamps and includes another delivery for event 1. The two latest versions of that event have identical source update and ingestion timestamps, deliberately making timestamp ordering alone insufficient. The payload amount on the selected tie winner is 999. This value is a test marker, not a revenue estimate. Counting deliveries as events would inflate downstream activity measures, while selecting an arbitrary tied payload would make reruns disagree even when row counts looked correct.

The investigation starts at the raw delivery grain. `investigation.sql` groups by event identity, counts deliveries, and exposes the most recent source timestamp. Its executed output is included in `results.json`. This establishes repeated input identities before inspecting the incremental target. It matters because configuring a unique key on a dbt incremental model does not automatically deduplicate the relation supplied to the adapter. Here the injected bug passes every delivery through unchanged, so multiple source rows can be inserted for the same key.

The fix ranks the incoming records by source update time descending, then ingestion time descending, then a stable delivery sequence descending. Source time establishes business recency; ingestion time resolves repeated arrivals of the same source version. The sequence supplies a declared final policy for exact timestamp ties. The generator guarantees distinct sequences within tied identities. A real source without such a stable field would require an explicit payload conflict policy before this ordering could be trusted. Physical row order is never the intended decision rule.

Run `make case-1` after `make setup`. The runner generates fixtures, loads the original batch, performs a full initial build, restores the late deliveries, and executes incremental models again. DuckDB uses dbt's delete-and-insert incremental strategy here; this illustrates the input deduplication requirement without claiming adapter-specific MERGE behavior. The fixed model reads the complete small source history on each run. A production optimization using a watermark would also need to handle events arriving behind that watermark and compare incoming versions against the existing target.

The regression query is applied to both models: duplicate groups must exist before the fix and disappear afterward. dbt also checks uniqueness and non-null event identities. Pytest checks the winning payload, a normal updated event, and the result under reversed physical input order. The committed evidence records the observed counts and tie winner; rerunning the commands regenerates it. This keeps the incident explanation tied to executed transformations rather than an illustrative narrative disconnected from code.
