# A stale table changes the apparent incident priority

Checking write history before prioritizing the apparent error reduced the measured active-window error rate from a misleading combined 20.75% to 1% in this synthetic investigation. The legacy table has an 80% historical error rate but no writes after 2024-01-01. The current table has writes through the fixed evaluation date, 2025-01-03. This changes the evidence available for triage; it does not repair historical rows or prove that all current processing is healthy. This is generated portfolio evidence, not a claim about a real organization's incident response.

The fixture represents a write audit containing table name, write date, rows written, and error rows. The legacy table contributes 1,000 historical rows, including 800 errors. The current table contributes 3,000 rows over three daily writes, including thirty errors. The injected bug aggregates both tables without considering when their data was written. The resulting 830 errors over 4,000 rows yield 20.75%. A dashboard presenting that number as ongoing loss would mix two different operational periods and could direct engineering attention toward a retired writer.

The investigation therefore starts with freshness evidence. `investigation.sql` groups the write history by table, exposes first and last write dates, and calculates each table's weighted error rate. The committed result shows that the high-error relation has a single old write date while the current relation continues receiving writes. The conclusion depends on this explicit synthetic audit being complete. In production, an old maximum event date alone could also indicate a stalled pipeline, a delayed source, or missing audit data; owner confirmation and independent write telemetry would be needed before declaring a table retired.

The fix defines an evaluation window beginning on 2025-01-01 and evaluates writes within that window. The date is fixed deliberately so future reruns reproduce the same historical investigation instead of drifting with the wall clock. It retains the old evidence in the source and the investigation output. No error rows are deleted or relabeled. The corrected aggregate is thirty errors divided by 3,000 current rows, or 1%. That supports separating historical cleanup from current operational triage while still leaving the current errors available for investigation.

Run `make case-3` after `make setup` to regenerate the write history, build both interpretations, and execute the checks. The regression uses a 2% demonstration threshold: the combined relation violates it and the active-window relation does not. This threshold is a fixture policy for exercising the test, not a recommended service-level objective. An actual priority decision would require business severity, affected users, and acceptable error budgets in addition to the rate and freshness information shown here.

The dbt singular test checks the fixed aggregate against that declared threshold. The runner also applies the same query to the broken model as a negative control, recording one violating aggregate before correction and zero afterward. Pytest verifies the legacy last-write date and the active error rate, connecting the triage conclusion back to the audit evidence. The JSON includes the evaluation date and grouped history so downstream readers can distinguish a change in measurement scope from a remediation outcome. This distinction is the central engineering lesson: establish whether the alarming evidence represents ongoing writes before using it to rank current incidents.
