# Incident 03: Dashboard revenue is higher than the ledger

> Generated by `casebook run 3`. Every number below is computed from the data.

## Symptom

Revenue in the dashboard is 15.3% above finance's ledger for the same period, and the gap only started on day 6.

## Investigation

| # | Hypothesis | Check | Finding | Verdict |
|---|---|---|---|---|
| 1 | Prices went up | Average amount per distinct order, before vs after the jump | 54.78 vs 55.07 | **rejected** |
| 2 | There were more orders | Distinct order events per day | 5,000 per day | **rejected** |
| 3 | The same event is stored more than once | Extra copies of an event_id in fct_orders | 0.0% of rows before day 6, 23.4% after | **confirmed** |
| 4 | Re-running a day adds it again | Load 2026-05-08 twice and compare revenue | revenue changes on every re-run | **confirmed** |

## Root cause

From day 6 the event stream delivers at least once, so about 8% of events arrive more than once. The load appends every batch as received, and appending is not safe to repeat: the re-run of 2026-05-08 added the whole day again.

## Fix

Give `fct_orders` a primary key on `event_id`. Each batch keeps one row per event (the latest `ingested_at`) and is upserted with `INSERT OR REPLACE`. Dedupe comes first: given the same key twice in one batch, the upsert silently keeps whichever copy it meets first, not the latest one.

## Guard

Two tests run in CI: `duplicate_share(fct_orders, event_id) == 0`, and `is_idempotent()` loads the same day twice and requires identical revenue.

## Before and after

| Metric | Before | After |
|---|---:|---:|
| Dashboard revenue vs ledger | +15.3% | 0.0% |
| Duplicate rows in fct_orders | 7,632 | 0 |
| Safe to re-run a day | no | yes |
