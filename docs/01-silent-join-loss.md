# Incident 01: Daily impressions dropped overnight

> Generated by `casebook run 1`. Every number below is computed from the data.

## Symptom

On 2026-03-14 the impressions report showed 5,962, down 70.2% from a normal day (20,000). No job failed and no alert fired.

## Investigation

| # | Hypothesis | Check | Finding | Verdict |
|---|---|---|---|---|
| 1 | The source sent less data | Raw impressions per day | 20,000 every day, no drop | **rejected** |
| 2 | Staging filtered rows out | Reconcile raw vs staging per day | 0 days with a gap | **rejected** |
| 3 | The report step loses rows | Reconcile staging rows vs report impressions per day | 3 days lose rows, 41,935 rows in total | **confirmed** |
| 4 | Lost rows belong to campaigns missing from the dimension | Anti-join staging to dim_campaigns | 8 campaign IDs, 41,935 rows, first seen 2026-03-12; dimension snapshot 2026-03-08 | **confirmed** |

## Root cause

The report joins impressions to `dim_campaigns` with an INNER JOIN. The dimension is a weekly snapshot (last one 2026-03-08). Campaigns launched on day 12 were not in it yet, so every impression for them was dropped silently.

## Fix

Use a LEFT JOIN and label rows with no campaign as `Unknown (not in dimension yet)`. Totals stay right, and the unknown share shows how stale the dimension is.

## Guard

`reconcile(stg_impressions, rpt_daily)` runs after every build and fails it if any day loses rows. A model that drops data now breaks loudly instead of quietly.

| Days where report ≠ staging | 3 | 0 |
